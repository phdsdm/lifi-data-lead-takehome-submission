# Reference snapshots

Two files here are not snapshots: `integrator_map.csv` and `token_class.csv` are maintained by hand, not fetched, and are described in their own sections at the end. Everything else is a committed snapshot of external reference data. `analysis/notebooks/01_reference_data.ipynb` fetched chains, tokens, tools, the 600-event status sample, CoinGecko prices and LI.FI's chain ids on 2026-10-28; `analysis/notebooks/03_transfer_status.ipynb` fetched the edge-case and 2,600-event status snapshots on 2026-10-28; `analysis/notebooks/07_transfer_status_extension.ipynb` fetched the $10k census of swap rows, the integrator strata and the bridge-only census on 2026-11-01. `lifi_api_transfer_status_fee_lines.csv` is derived from the status responses with no network call.

The raw API responses behind these files (112 MB of JSONL) are not in this repository; this folder holds the flattened CSVs the queries read. The notebooks are committed executed as the record of each fetch, and they read those raw files, so they cannot be re-run as they stand. `snapshot_manifest.json` was written by the notebooks at fetch time and is the source of the fetch times and row counts below. API keys were read from the environment and never written to a file: the CoinGecko demo key from `COINGECKO_API_KEY`, the LI.FI key from `LIFI_API_KEY`. Notebook 03 paced its calls and read the `ratelimit-*` response headers; the minimum `ratelimit-remaining` over its calls was 41 of 100. Notebook 07 paced at 0.1 s, waited for `ratelimit-reset` when `ratelimit-remaining` fell below 3, and recorded HTTP 429s per call as `retries_429`.

## The `/v1/status` files

These come from the same endpoint, `https://li.quest/v1/status`. They stay separate because each was selected differently, and the selection decides what a file can support. A transaction can appear in more than one file: the four files queries read per transfer (`sample_2600`, `edge_cases`, `extension`, `bridge_census`) hold 8,105 rows for 7,901 distinct transactions.

| File (`lifi_api_transfer_status_…`) | Rows | How the transfers were selected | What it supports |
|---|---|---|---|
| `sample_2600.csv` | 2,600 | `uniform_2000`: uniform random draw from the file. `equal_per_chain_600`: 100 per source chain (`sample_design`) | The uniform 2,000 is the sample that estimates rates across the file |
| `edge_cases.csv` | 328 | The 294 unusual rows the data profile found, one row per lookup | Explains specific rows; not representative |
| `extension.csv` | 4,868 | `census_swap_10k`: every swap row at $10,000 or more. `integrator_strata`: a sample per integrator string over its swap rows. Use `in_census` and `in_strata`, since 48 rows are in both | Complete above $10k on swap rows; rates per integrator |
| `bridge_census.csv` | 309 | `census_bridge_100k`: every row without a source swap at $100,000 or more | Complete above $100k on bridge-only rows |
| `fee_lines.csv` | 6,066 | Derived, not fetched: one row per fee line of the `sample_2600` and `edge_cases` responses | Fee detail per line; a different grain from the others |

Notebooks 01 and 03 and the `in_sample_600` column of `edge_cases` refer to `sample_600`, the first fetch of 600 events. That file is not in this repository, because all 600 are in `sample_2600`. Where a row reuses a response fetched earlier, `reused_from` holds the name of the raw file it came from.

What each metric means, in DefiLlama's methodology text and the adapter:

- `dailyFees`: "All fees paid by users on LI.FI bridges [swaps on the `dex` series], including integrator fees." The USD value of the `FeesCollected` and `FeesForwarded` events on each chain, at DefiLlama's prices, without the tokens on its blacklist (`getDefaultDexTokensBlacklisted`, whose list is not in this snapshot).
- `dailyRevenue`: "Share of fees kept by LI.FI." The `_lifiFee` part of `FeesCollected`, and the `FeesForwarded` amounts paid to LI.FI's recipient address. **The adapter at the commits below excludes Jumper from 2026-08-07:** a `FeesForwarded` transaction whose only integrator is one of four tags (`jumper.exchange`, `jumper.exchange.gas`, `jumperadvanced`, `jumperrwa`) counts as integrator fee. ## The integrator map (maintained, not fetched)

`integrator_map.csv` is the normalisation map: a checked table, not a pattern. Nothing fetched it. Query `64_integrator_map_proposal` applies the normalisation rules to every raw string, and the committed file is that proposal after a manual check. The same query shows, per string, where the committed file departs from the proposal (`departs`). The file was edited by hand after that, and query 64 shows each change as a departure.

- `lifi-build-db` loads it as `ref_integrator_map` with no code change, like every CSV here.
- **The empty string.** One raw `integrator` is the empty string (2 rows). The file writes it as an empty field, which pandas reads as missing, so `ref_integrator_map.integrator` is NULL on that row. Join on `coalesce(m.integrator, '') = t.integrator`: a plain equality join leaves the 2 rows unmapped. Its `partner` is `(empty string)`.
- **Classes.** `partner` (ranked and counted as an integrator, underscore strings included and flagged), `lifi_product` (LI.FI's own products: inside started volume, flagged, not ranked), `unattributed_api` (`lifi-api`, its family member `lifi-sdk`, and the empty string), `test_or_dev` (contains `test`, `dev`, `local`, `staging` or `stg`, case-insensitive: out of partner counts, in total volume; plus `whitewallet-qa` and `hashport-wallet-e2e`, entered by hand because the substring list was not extended).
- **Partner names.** The seven variant families of `61_integrator_name_families` and `tangem`/`tangem-pay-prod` merge into one name each; a family's name is its member with the most rows that is not `test_or_dev`. A `test_or_dev` member keeps its family's name, so a partner's test traffic stays linked to it. The link is extended by hand to test strings outside a family whose partner is in the map: `dev.jumper.exchange` and `stg.jumper.exchange` under `jumper.exchange`, `Reah-STG` under `Reah-PRD`, `hashport-wallet-e2e` under `HashPort-Wallet-Prod`. Every other string is its own partner.
- **When the data changes.** A new export brings strings the map does not have: `64_integrator_map_proposal` shows them with `departs` true and an empty `map_class`, and `65_started_volume` counts their rows in `rows_not_in_map`.

## The token class table (maintained, not fetched)

`token_class.csv` gives each token symbol a class, used for the pair classes of queries 158 to 179. Nothing fetched it: 28 symbols are `stable` and 26 `major` by lists set during the analysis, and the other 691 are `alt`. No external source defines the classes.

- `lifi-build-db` loads it as `ref_token_class` with no code change, like every CSV here.
- **A symbol not in the table is `alt`.** Queries read it with `coalesce(class, 'alt')`; the table lists the snapshots' symbols so that a new one is visible, not to change that default.
- **Pair class.** A pair is `alt` if either side is `alt`, else `major` if either side is `major`, else `stable`.
- **Symbols, not addresses.** The table keys on the status API's symbol, so two tokens sharing a symbol share a class. Thirteen listed symbols appear in no status snapshot (`crvUSD`, `RLUSD`, `TUSD`, `sUSD`, `AUSD`, `apxUSD`, `USDH`, `tBTC`, `LBTC`, `WSOL`, `ADA`, `MATIC`, `WMATIC`).
- **Judged misclassified, not changed.** Query `160_token_class_review` flags the largest symbols a reader would class otherwise (`XAUt`, `EURC`, `EURe`, `WAVAX`, `BTCB`, `PYUSD0` and others), with the volume each carries. A change moves queries 165 to 172.
